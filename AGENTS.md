# Инструкции для Codex

- Перед значительным этапом прочитай [концепцию проекта](docs/PROJECT_VISION.md), сверься с [дорожной картой](docs/ROADMAP.md) и изучи текущее состояние репозитория. Определи минимальный объём изменений и составь краткий план.
- Выполняй только согласованный этап. Проверь его по критериям готовности, зафиксируй результат и следующий шаг. Долгосрочные возможности учитывай при выборе модели данных и контракта расширений.
- Соблюдай порядок приоритетов из концепции. Используй Python/FastAPI, React/TypeScript и SQLite. Проверяй локальный запуск в Debian под WSL без Docker и интерфейс в браузере Windows.
- Оставляй в ядре общие функции платформы. Размещай каждую интеграцию в отдельном плагине. Различай Plugin и WidgetInstance, храни функциональные настройки экземпляра отдельно от оформления.
- Сохраняй работоспособность пустого ядра и остальных виджетов при сбое плагина. При отсутствии плагина показывай заглушку, сохраняя данные экземпляра.
- Проектируй взаимодействия прежде всего для сенсорного экрана, проверяй базовые действия мышью и навигацию с клавиатуры.
- Соблюдай границы MVP из раздела 9 концепции. Доступ ограничен доверенной сетью, секреты интеграций обрабатываются на сервере.
- После реализации и проверок каждого согласованного этапа создавай локальный коммит с целевыми изменениями. Сохраняй отдельно подготовленные пользователем файлы в индексе.

## Версии в сообщениях коммитов

Начинай сообщение коммита с версии `vX.Y.Z`, где X, Y и Z — целые неотрицательные числа. Выбирай номер от последней версии в истории проекта по масштабу изменений. После версии можно через пробел кратко описать, что изменилось, например `v0.4.3 Исправлено сохранение размера виджета`.

- Увеличивай X при крупном релизе, например `v0.4.2` → `v1.0.0`.
- Увеличивай Y при глобальном обновлении, например при существенном изменении ядра: `v0.4.2` → `v0.5.0`.
- Увеличивай Z для небольших функций, исправлений, правок документации и оформления, например `v0.4.2` → `v0.4.3`.
