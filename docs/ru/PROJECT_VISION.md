# RaspberryPi-Home-IT-Terminal

## Глобальная цель проекта

Разработать открытую модульную веб-платформу RaspberryPi-Home-IT-Terminal, превращающую Raspberry Pi 5 в интерактивный домашний IT-терминал с сенсорным экраном.

Приложение должно одновременно выполнять роль информационной панели, системы мониторинга и универсальной платформы для пользовательских виджетов.

GitHub: https://github.com/Vanillllla/RaspberryPi-Home-IT-Terminal

### 1. Среда разработки и развёртывания

Разработка ведётся на Debian в WSL под Windows. Тестирование интерфейса осуществляется через браузер на Windows-компьютере.

В дальнейшем приложение будет работать непосредственно на Raspberry Pi 5 (8 ГБ RAM) с горизонтальным сенсорным экраном 7–10 дюймов.

Требования:

- Backend: Python, FastAPI.
- Frontend: React, TypeScript.
- Хранение данных: SQLite.
- Обновление данных: REST API и WebSocket там, где это необходимо.
- Локальное развёртывание без Docker.
- Автоматический запуск на Raspberry Pi через systemd в будущем.
- Возможность открыть интерфейс в браузере с других устройств локальной сети или через доверенную VPN-сеть.
- Основной режим эксплуатации Raspberry Pi — Chromium Kiosk Mode.

### 2. Философия архитектуры

Главная ценность проекта — модульность и расширяемость.

Ядро отвечает за рабочие столы, размещение виджетов, настройки, хранение состояния, профили, интерфейс и управление жизненным циклом расширений.

Виджеты являются независимыми плагинами. Ядро не должно содержать специализированной логики конкретных виджетов.

Ключевые требования:

1. Приложение должно корректно запускаться без единого установленного плагина.
2. Установка нового плагина не должна требовать ручного изменения исходного кода ядра.
3. Ошибка или отсутствие плагина не должны ломать остальные виджеты и рабочие столы.
4. При отсутствии плагина его экземпляры отображаются заглушками без потери настроек.
5. Один плагин может иметь множество экземпляров с независимыми настройками и оформлением.
6. Архитектура должна допускать последующую реализацию визуального конструктора и редактора Python-кода.
7. Внутренняя модель данных должна поддерживать будущие профили, темы, оформление и новые типы компонентов.

Избегать преждевременной абстракции и избыточной сложности. Предусмотреть необходимые точки расширения, но не реализовывать будущую функциональность заранее.

### 3. Рабочие столы

Интерфейс напоминает минималистичный рабочий стол Android с виджетами.

- Несколько независимых страниц.
- Переключение горизонтальными свайпами.
- Переключение мышью и клавиатурой.
- Поддержка Ctrl + Left / Ctrl + Right.
- Колёсико мыши не используется для переключения.
- Размещение виджетов на сетке.
- Изменение размеров виджетов.
- Перетаскивание после длительного удержания.
- Сохранение расположения после изменений.
- Возможность открытия расширенного интерфейса поверх рабочего стола.

Сенсорный экран является приоритетом, но все базовые функции должны работать мышью в обычном браузере.

### 4. Система плагинов

Каждый плагин располагается в отдельной папке внутри `plugins/`.

Структура плагина должна предусматривать:

- Manifest с идентификатором, версией, описанием и возможностями.
- React-компонент компактного виджета.
- Необязательный React-компонент расширенного интерфейса.
- Необязательный компонент настроек.
- Необязательный Python backend.
- Собственные ресурсы и зависимости.

Нужно определить стабильный API и контракт плагинов, который позволит развивать систему без постоянного изменения ядра.

На ранних этапах допускается пересборка frontend и перезапуск backend после добавления нового плагина. В дальнейшем должна быть возможна динамическая установка пакетов.

### 5. Структура экземпляров виджетов

Разделить понятия Plugin и WidgetInstance.

Plugin — описание функциональности и исходный код.

WidgetInstance — конкретное размещение плагина на рабочем столе.

Экземпляр имеет собственные идентификатор, настройки, оформление, размеры, позицию и привязку к рабочему столу.

Настройки функциональности не должны быть жёстко связаны с настройками оформления.

### 6. Интерфейс виджетов

Предусмотреть три независимых представления:

- Widget — компактное отображение на рабочем столе.
- Details — необязательное расширенное окно почти на весь экран.
- Settings — настройки конкретного экземпляра.

Расширенное окно открывается поверх текущего рабочего стола, имеет кнопку закрытия и не является отдельной страницей рабочего стола.

Элементы управления внутри виджета должны оставаться интерактивными и не конфликтовать с перемещением или свайпами.

### 7. Оформление

Начальный дизайн — минималистичный, адаптивный, с аккуратными карточками и скруглениями.

Сразу предусмотреть централизованные дизайн-токены и разделение оформления и функциональности.

В дальнейшем добавить темы, обои, прозрачность, градиенты, цвета, размеры и индивидуальное оформление экземпляров.

Не реализовывать полноценную кастомизацию в первой версии.

### 8. Профили

В первой версии достаточно одного профиля, но модель данных не должна препятствовать расширению.

В будущем профили будут храниться на сервере и содержать собственные рабочие столы, расположение экземпляров и настройки отображения.

Должен существовать механизм последующего автоматического выбора профиля по размеру или классу устройства с ручным переключением.

### 9. Безопасность и доступ

Первая версия предназначена для одного пользователя в доверенной локальной среде.

На этапе MVP авторизация и подтверждения действий не реализуются. Не создавать в этой версии функций, выполняющих потенциально опасные административные операции на внешних системах.

Не открывать приложение в публичный интернет. Секреты будущих интеграций должны обрабатываться на серверной стороне.

Архитектура должна позволять в будущем добавить авторизацию, права доступа, разрешения плагинов и изоляцию их исполнения.

### 10. Планируемые интеграции

Будущие плагины:

- Часы и календарная дата.
- Проверка доступности VPN-серверов Hysteria 2.
- Мониторинг Proxmox, виртуальных машин, CPU, RAM и GPU.
- Home Assistant.
- Мониторинг локальной сети.
- Пользовательские HTTP/API-интеграции.
- Другие плагины сторонних разработчиков.

Все интеграции должны оставаться независимыми от ядра.

### 11. Будущее развитие

Предусмотреть архитектурную возможность добавления:

- Графического конструктора виджетов.
- Редактора Python-обработчиков.
- Установки виджетов из ZIP.
- Публичной библиотеки или маркетплейса плагинов.
- Управления разрешениями и зависимостями.
- Нескольких профилей.
- Полноценной кастомизации.
- Раздельного исполнения сложных плагинов.

Это долгосрочные направления, а не требования к первой версии.

## Правила работы над проектом

Разрабатывать проект строго итерационно.

Не пытаться реализовать всю глобальную цель за один запрос.

Перед началом значительного этапа:

1. Изучить текущее состояние репозитория.
2. Определить минимальный объём изменений.
3. Сформировать краткий план.
4. Реализовать только согласованный этап.
5. Проверить работоспособность.
6. Зафиксировать результат и следующие шаги.

Приоритеты:

1. Корректная архитектура.
2. Модульность.
3. Работоспособность.
4. Простота поддержки и расширения.
5. Визуальное оформление.
6. Дополнительные функции.

Не добавлять функциональность на будущее без необходимости. Сохранять точки расширения.

Главная долгосрочная цель — создать устойчивое ядро, на основе которого новые виджеты можно разрабатывать, добавлять, настраивать и удалять независимо от основной системы.
